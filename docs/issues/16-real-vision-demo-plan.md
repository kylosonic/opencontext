# Real vision demo: implementation plan

Status: PROPOSED — waiting for approval

## Objective

Provide an optional, documented way to inspect real vision output from the
local Compose demo while retaining the existing credential-free fixture stack as
the default. The change reuses the OpenAI-compatible vision adapter already in
the worker; it does not add a provider SDK or a new web interface.

This proposal does not claim broad model quality, adoption, contributor
activity, or performance. Any real-model output is a provider and model
dependent demonstration, not a published quality measurement.

## Proposed user flow

Keep these commands unchanged for the default demo:

```bash
npm run fixture
docker compose up --build
```

Add an opt-in path:

```bash
export OPENCONTEXT_DEMO_VISION=real
export OPENAI_BASE_URL=https://your-openai-compatible-host/v1
export OPENAI_API_KEY=...
export VISION_MODEL=<image-capable model>
docker compose up --build
```

The Compose worker selects `VISION_PROVIDER=openai_compatible` only when
`OPENCONTEXT_DEMO_VISION=real`. Unset or `fixture` continues to use
`VISION_PROVIDER=fixture`.

Provider values remain directly overridable for operators who already use the
worker settings. An existing opt-in smoke test validates the selected model
without starting the web and worker:

```bash
cd workers/processor
OPENCONTEXT_OPENCODE_E2E=1 pytest tests/test_opencode_vision_smoke.py -q
```

That test currently reads `OPENCODE_API_KEY` (or the local OpenCode
authentication export); it reuses `OPENAI_BASE_URL` and `VISION_MODEL`. The
plan should check that the same credential contract covers the proposed
OpenAI-compatible opt-in path for providers outside OpenCode.

The committed hold-out reference for the local demo should be a simple image
with legible text and a few UI features, rather than a test-pattern video. Its
source and expected visible terms should be documented. Do not describe overlap
with that image as an independent accuracy benchmark.

No database schema, Prisma migration, web route, job API, or evidence format
needs to change. The existing image upload route and evidence review interface
can display real provider output without modification.

## Configuration and safety

- Preserve `VISION_PROVIDER=fixture`, `TRANSCRIPTION_PROVIDER=faster_whisper`,
  and the existing fixture labels as the untouched defaults.
- Make real mode fail before starting the worker if the key, base URL, or
  vision model is missing. The error must name variables but never include
  their values.
- Pass secrets through environment variables or ignored local files. Do not
  commit them, bake them into an image, or print them in logs.
- Keep the real-provider call opt-in and bounded. Do not make a routine CI job
  depend on a live third-party model.
- Clearly identify the real demo's output as generated by the configured
  provider and model. The fixture path remains visibly labeled fixture data.
- Do not send the demo media to a real provider without a deliberate operator
  action. Never infer approval from a missing API key or a previous fixture run.

## Risks and tradeoffs

- **Provider variability:** a model change can change observations, visible
  text, latency, or cost. Record the actual model and provider settings for a
  demonstration, without centralizing credentials in documentation.
- **Network and billing dependency:** the opt-in path can fail on outages,
  rate limits, or account permissions, and a provider may charge for calls.
- **Image content:** images are sent to the configured service. Use a synthetic,
  non-sensitive reference by default and explain the privacy boundary.
- **Local startup complexity:** an added mode must not make the fixture command
  harder or accidentally start making external calls.
- **False quality interpretation:** an output that correctly recognizes a
  deliberately simple image is not evidence of general vision quality. The docs
  must say this next to the example.
- **Image generation dependency:** a generated image needs a reproducible
  renderer. A small, attributed static PNG avoids inconsistent fonts across
  developer machines.
- **Compose validation:** the current hosted Compose definition requires a key
  during interpolation, so `docker compose config` needs an explicit dummy
  input. The local demo must provide a safe configuration check without trying
  to make a provider request or weakening the production requirement.

## Testing plan

1. Start without `OPENCONTEXT_DEMO_VISION` and confirm the worker remains on the
   fixture provider, makes no model call, and labels each observation as fixture
   output.
2. Select real mode without credentials and confirm startup stops with a safe,
   actionable configuration error.
3. Select real mode with an approved test provider and model; verify startup,
   then analyze the committed hold-out image through the normal upload flow.
4. Confirm the result contains provider-derived observations, visible text, and
   evidence IDs; copy and download Markdown and JSON successfully.
5. Run the provider check without printing the key. Record the provider, model,
   date, and observable result, not a generalized accuracy claim.
6. Run the full worker suite for the fixture default. Run the Compose fixture
   smoke test to ensure the default remains functional. For the proposed opt-in
   real path, capture equivalent upload and export evidence; do not replace the
   routine offline CI check with a network-dependent test.
7. Inspect the docs and demo in the in-app browser on desktop and mobile.
   Verify fixture labels remain visible and the opt-in instructions do not
   imply that a live provider is configured by default.

The hold-out flow should be implemented as an extension of
`docs/issues/11-compose-e2e.md`, not as a second unrelated Compose smoke harness.

## Acceptance criteria

- `docker compose up --build` still starts the credential-free fixture demo.
- Real vision is enabled only by the explicit opt-in selector.
- A missing key or model produces a safe startup error, never a fixture
  observation mislabeled as real vision.
- The opt-in upload, vision analysis, evidence view, and both exports are
  verified against a chosen provider before documentation calls them usable.
- Any external call is documented as a third-party transmission and a possible
  billing event.
- No fixture or adoption/quality metric is presented beyond what was measured.

## Out of scope

- A model leaderboard or general accuracy score.
- Automatic fallback from a failed real model call to fixture output.
- New cloud infrastructure, hosted credentials, or a hosted-provider UI.
- Changes to upload limits, the job lifecycle, or the output schema.
